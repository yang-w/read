**CHAPTER 8**

### Type Declarations and @types

### Item 65: Put TypeScript and @types in devDependencies

npm dependency types in `package.json`:

- **dependencies** — packages required to run your JavaScript at runtime. Installed transitively when others install your package.
- **devDependencies** — packages used to develop and test your code, not required at runtime. Not installed transitively.
- **peerDependencies** — packages required at runtime that the consumer is responsible for providing (e.g., a React component library specifying which versions of React it supports).

TypeScript is a development tool and TypeScript types do not exist at runtime, so packages related to TypeScript generally belong in `devDependencies`.

**TypeScript itself** should be a `devDependency`:
- Avoids version mismatch between team members.
- Avoids a manual setup step.
- Run the npm-installed version via: `$ npx tsc`

**@types packages** (from DefinitelyTyped) should also be `devDependencies`, even when the corresponding package is a `dependency`:

```
$ npm install react
$ npm install --save-dev @types/react
```

Resulting `package.json`:

```
{
"devDependencies" : {
"@types/react" : "^18.2.23",
"typescript" : "^5.2.2"
},
"dependencies" : {
"react" : "^18.2.0"
}
}
```

You publish JavaScript, not TypeScript — your JavaScript does not depend on `@types` at runtime.

Advantages of putting `@types` in `devDependencies` even for non-published web apps:
- `npm install --production` installs only prod deps, resulting in slimmer production images.
- Automated tools like Renovate/Dependabot can be configured to prioritize production deps (which are more likely to have security-relevant updates).

**Things to Remember**

- Understand the difference between dependencies and devDependencies in `package.json`.
- Put TypeScript in your project's devDependencies. Don't install TypeScript system-wide.
- Put @types dependencies in devDependencies, not dependencies.

### Item 66: Understand the Three Versions Involved in Type Declarations

Three versions involved in an `@types` dependency:

1. The version of the package itself
2. The version of its type declarations (`@types`)
3. The version of TypeScript

**Version matching semantics:**

```
$ npm install react
+ react@18.2.0
$ npm install --save-dev @types/react
+ @types/react@18.2.23
```

- Major/minor (`18.2`) should match — these track the library's API version.
- Patch versions (`.0` vs `.23`) will differ — `@types` patches fix declaration bugs and omissions independently of the library.

**Ways version matching can go wrong:**

**1. Library updated, types not updated:**
- Symptom: type errors when using new library features; potential runtime errors despite passing type checking if there were breaking changes.
- Fix: update `@types` to match; or augment types in your project (Item 71); or contribute updated declarations.

**2. Types ahead of library:**
- Happens when installing typings for a library you previously declared as `any`.
- Symptom: type checker validates against a newer API than what runs at runtime.
- Fix: upgrade the library or downgrade the type declarations.

**3. Type declarations require a newer TypeScript than you use:**
- Symptom: type errors inside the `@types` declarations themselves.
- Fix: upgrade TypeScript; use an older `@types` version; or stub with `declare module`.
- Some packages use `typesVersions` to provide different declarations per TypeScript version (rare, but used by `@types/node`, `@types/react`).
- Install `@types` for a specific TypeScript version: `npm install --save-dev @types/react@ts4.9`

**4. Duplicate @types dependencies:**
- Happens when `@types/foo` and `@types/bar` require incompatible versions of a shared `@types` dependency. npm installs both in a nested structure:

```
node_modules/
@types/
foo/
index.d.ts @1.2.3
bar/
index.d.ts
node_modules/
@types/
foo/
index.d.ts @2.3.4
```

- Declarations live in a flat global namespace — duplicates cause errors about duplicate or non-mergeable declarations.
- Diagnose: `npm ls @types/foo`
- Fix: update `@types/foo` or `@types/bar` so they depend on compatible versions.

**Bundled types vs. DefinitelyTyped:**

Packages can bundle types via a `"types"` field in `package.json`:

```
{
"name" : "left-pad",
"version" : "1.3.0",
"description" : "String left pad",
"main" : "index.js",
"types" : "index.d.ts"
// ...
}
```

Bundling solves version mismatch (especially when generated by `tsc --declaration`), but has downsides:

- A bug in bundled types that can't be fixed via augmentation (Item 71) may block you from upgrading TypeScript. DefinitelyTyped types are continuously tested against new TypeScript releases and fixed quickly.
- If your types depend on another library's `@types`, that must be either a `devDependency` (not installed by consumers) or a `dependency` (forces `@types` on JavaScript users). DefinitelyTyped handles this cleanly.
- Patching types for old library versions is harder in your own repo; DefinitelyTyped has mechanisms for multi-version maintenance.
- DefinitelyTyped is community-maintained and handles high patch volumes; bundling means you own that maintenance burden.

Official recommendation: bundle types only if the library is written in TypeScript (so `tsc` can generate them automatically). For JavaScript libraries, publish on DefinitelyTyped.

**Things to Remember**

- There are three versions involved in an @types dependency: the library version, the @types version, and the TypeScript version.
- Recognize the symptoms of different types of version mismatch.
- If you update a library, make sure you update the corresponding @types.
- Understand the pros and cons of bundling types versus publishing them on DefinitelyTyped. Prefer bundling types if your library is written in TypeScript, and DefinitelyTyped if it is not.

### Item 67: Export All Types That Appear in Public APIs

Any type that appears in a public API is effectively exported even if not explicitly — users can extract it using `Parameters` and `ReturnType`.

Example with unexported types:

```
interface SecretName {
first: string ;
last: string ;
}

interface SecretSanta {
name: SecretName;
gift: string ;
}

export function getGift(name: SecretName, gift: string ): SecretSanta {
// ...
}
```

Users cannot directly import `SecretName` or `SecretSanta`, but can extract them:

```
type MySanta = ReturnType< typeof getGift>;
// ^? type MySanta = SecretSanta
type MyName = Parameters< typeof getGift>[0];
// ^? type MyName = SecretName
```

By putting these types in a public API signature, you have already committed to them. Not exporting them only inconveniences users without providing flexibility.

**Things to Remember**

- Export types that appear in any form in any public method. Your users will be able to extract them anyway, so you may as well make it easy for them.

### Item 68: Use TSDoc for API Comments

Inline comments are not surfaced by editors in tooltips. JSDoc/TSDoc-style comments (`/** ... */`) are shown when calling a function.

```
// Generate a greeting. Result is formatted for display.
function greet(name: string , title: string ) {
return `Hello ${title} ${name}`;
}
```

vs.

```
/** Generate a greeting. Result is formatted for display. */
function greetJSDoc(name: string , title: string ) {
return `Hello ${title} ${name}`;
}
```

Use `@param` and `@returns` for per-parameter documentation shown as you type a call:

```
/**
* Generate a greeting.
* @param name Name of the person to greet
* @param title The person's title
* @returns A greeting formatted for human consumption.
*/
function greetFullTSDoc(name: string , title: string ) {
return `Hello ${title} ${name}`;
}
```

TSDoc also works on type definitions — field-level docs appear in editor tooltips:

```
/** A measurement performed at a time and place. */
interface Measurement {
/** Where was the measurement made? */
position: Vector3D;
/** When was the measurement made? In seconds since epoch. */
time: number ;
/** Observed momentum */
momentum: Vector3D;
}
```

- Documentation on individual fields is carried through homomorphic mapped types (`Partial`, `Pick`, etc.).
- Use `@template` to document type parameters for generic types.
- TSDoc comments support Markdown (bold, italic, lists).
- Avoid JSDoc type annotations (`@param {string} name`) — use TypeScript types instead (Item 31).
- Mark deprecated symbols with `@deprecated` — editors render them with strikethrough, visible without hovering. Always include a reference to the replacement or deprecation docs.

**Things to Remember**

- Use JSDoc-/TSDoc-formatted comments to document exported functions, classes, and types. This helps editors surface information for your users when it's most relevant.
- Use @param, @returns, and Markdown for formatting.
- Avoid including type information in documentation (see Item 31).
- Mark deprecated APIs with @deprecated.

### Item 69: Provide a Type for this in Callbacks if It's Part of Their API

`this` is dynamically scoped (value depends on call site, not definition site), unlike `let`/`const` which are lexically scoped.

```
class C {
vals = [1, 2, 3];
logSquares() {
for ( const val of this .vals) {
console.log(val ** 2);
}
}
}

const c = new C();
c.logSquares();
```

Pulling out `logSquares` severs the `this` binding:

```
const c = new C();
const method = c.logSquares;
method();
```

Runtime error:

```
for (const val of this.vals) {
^
TypeError: Cannot read properties of undefined (reading 'vals')
```

`c.logSquares()` does two things: calls `C.prototype.logSquares` and binds `this` to `c`. Pulling out the reference separates them.

Fix with `call`:

```
const c = new C();
const method = c.logSquares;
method.call(c); // Logs the squares again
```

The DOM uses `this` in event handlers:

```
document.querySelector('input')?.addEventListener('change', function (e) {
console.log( this ); // Logs the input element on which the event fired.
});
```

**Common pitfall in classes — broken `this` in callbacks:**

```
class ResetButton {
render() {
return makeButton({text: 'Reset', onClick: this .onClick});
}
onClick() {
alert(`Reset ${ this }`);
}
}
```

Clicking alerts "Reset undefined" due to lost `this` binding.

**Fix 1 — bind in constructor:**

```
class ResetButton {
constructor () {
this .onClick = this .onClick.bind( this );
}
render() {
return makeButton({text: 'Reset', onClick: this .onClick});
}
onClick() {
alert(`Reset ${ this }`);
}
}
```

The prototype property `onClick` is shadowed by the bound instance property created in the constructor.

**Fix 2 — arrow function property (preferred shorthand):**

```
class ResetButton {
render() {
return makeButton({text: 'Reset', onClick: this .onClick});
}
onClick = () => {
alert(`Reset ${ this }`); // "this" refers to the ResetButton instance.
}
}
```

Generated JavaScript:

```
class ResetButton {
constructor() {
this .onClick = () => {
alert(`Reset ${ this }`); // "this" refers to the ResetButton instance.
};
}
render() {
return makeButton({ text: 'Reset', onClick: this .onClick });
}
}
```

**Typing `this` in callbacks:**

If a library sets `this` in callbacks, model it with a `this` parameter:

```
function addKeyListener(
el: HTMLElement,
listener: ( this : HTMLElement, e: KeyboardEvent) => void
) {
el.addEventListener('keydown', e => listener.call(el, e));
}
```

`this` is a special parameter — not a positional argument. Calling it with two args:

```
function addKeyListener(
el: HTMLElement,
listener: ( this : HTMLElement, e: KeyboardEvent) => void
) {
el.addEventListener('keydown', e => {
listener(el, e);
// ~ Expected 1 arguments, but got 2
});
}
```

TypeScript enforces calling with correct `this` context:

```
function addKeyListener(
el: HTMLElement,
listener: ( this : HTMLElement, e: KeyboardEvent) => void
) {
el.addEventListener('keydown', e => {
listener(e);
// ~~~~~~~~ The 'this' context of type 'void' is not assignable
// to method's 'this' of type 'HTMLElement'
});
}
```

User of the function gets full type safety:

```
declare let el: HTMLElement;
addKeyListener(el, function (e) {
console.log( this .innerHTML);
// ^? this: HTMLElement
});
```

Arrow functions in callbacks override `this` — TypeScript catches the mismatch:

```
class Foo {
registerHandler(el: HTMLElement) {
addKeyListener(el, e => {
console.log( this .innerHTML);
// ~~~~~~~~~ Property 'innerHTML' does not exist on 'Foo'
});
}
}
```

Avoid dynamic `this` binding in new APIs — arrow functions make it harder to use, and it is a historical source of confusion.

**Things to Remember**

- Understand how this binding works.
- Provide a type for this in callbacks if it's part of your API.
- Avoid dynamic this binding in new APIs.

### Item 70: Mirror Types to Sever Dependencies

**Problem:** Publishing a library whose type declarations depend on `@types/node` causes issues for web TypeScript users who don't use Node.js.

Example CSV parser:

```
// parse-csv.ts
import {Buffer} from 'node:buffer';

function parseCSV(contents: string | Buffer): {[column: string ]: string }[] {
if ( typeof contents === 'object') {
// It's a buffer
return parseCSV(contents.toString('utf8'));
}
// ...
}
```

Generated `.d.ts` file:

```
// parse-csv.d.ts
import { Buffer } from 'node:buffer';
export declare function parseCSV(contents: string | Buffer): {
[column: string ]: string ;
}[];
```

With `@types/node` as a `devDependency`, web TypeScript users get:

```
Cannot find module 'node:buffer' or its corresponding type declarations.
```

Making `@types/node` a `dependency` causes new complaints:
- JavaScript devs wonder why they depend on `@types` modules.
- TypeScript web devs wonder why they depend on Node.js.
- TypeScript Node.js devs with a different Node version get duplicate type definitions.

**Solution — use structural typing to define only what you need:**

```
export interface CsvBuffer {
toString(encoding?: string ): string ;
}
export function parseCSV(
contents: string | CsvBuffer
): {[column: string ]: string }[] {
// ...
}
```

A real Node.js `Buffer` is structurally compatible with `CsvBuffer`, so Node.js users can still pass one:

```
parseCSV( new Buffer("column1,column2\nval1,val2", "utf-8")); // OK
```

Give the interface a structural name to clarify intent:

```
/** Anything convertible to a string with an encoding, e.g. a Node buffer. */
export interface StringEncodable {
toString(encoding?: string ): string ;
}
```

Write a unit test to verify the assignability assumption (this test can use `@types/node` as a `devDependency` without affecting consumers):

```
import {Buffer} from 'node:buffer';
import {parseCSV} from './parse-csv';

test('parse CSV in a buffer', () => {
expect(
parseCSV( new Buffer("column1,column2\nval1,val2", "utf-8"))
).toEqual(
[{column1: 'val1', column2: 'val2'}]
);
});
```

If more `Buffer` methods are needed, add them to your mirrored interface. If the dependency grows large, consider vendoring (copying) the relevant portion. As the Go community says: "a little copying is better than a little dependency."

This technique also applies to severing dependencies between unit tests and production systems.

**Things to Remember**

- Avoid transitive type dependencies in published npm modules.
- Use structural typing to sever dependencies that are nonessential.
- Don't force JavaScript users to depend on @types. Don't force web developers to depend on Node.js.

### Item 71: Use Module Augmentation to Improve Types

**Problem:** `JSON.parse` returns `any` in TypeScript's built-in declarations:

```
declare let apiResponse: string ;

const response = JSON.parse(apiResponse);
const cacheExpirationTime = response.lastModified + 3600;
// ^? const cacheExpirationTime: any
```

`any` spreads silently through your code, undermining type safety and language services.

**Solution — declaration merging to override `JSON.parse` return type:**

Interfaces participate in declaration merging (repeated definitions of the same interface are merged). Built-in `lib.es5.d.ts`:

```
interface JSON {
parse(
text: string ,
reviver?: ( this : any , key: string , value: any ) => any
): any ;
// ...
}
declare var JSON: JSON;
```

Add your own declaration file:

```
// declarations/safe-json.d.ts
interface JSON {
parse(
text: string ,
reviver?: ( this : any , key: string , value: any ) => any
): unknown ;
}
```

Works like a function overload (Item 52) — since your code is loaded after libs, your overload wins. `JSON.parse` now returns `unknown`:

```
const response = JSON.parse(apiResponse);
// ^? const response: unknown
const cacheExpirationTime = response.lastModified + 3600;
// ~~~~~~~~ response is of type 'unknown'.
```

Requires an assertion, which is what you want:

```
interface ApiResponse {
lastModified: number ;
}
const response = JSON.parse(apiResponse) as ApiResponse;
const cacheExpirationTime = response.lastModified + 3600; // ok
// ^? const cacheExpirationTime: number
```

Same technique for `fetch` API:

```
// declarations/safe-response.d.ts
interface Body {
json(): Promise< unknown >;
}
```

**Banning problematic constructs — "knocking out" overloads:**

`new Set('abc')` silently iterates characters:

```
> new Set('abc')
Set(3) { 'a', 'b', 'c' }
```

Both `new Set('abc')` and `new Set(['abc'])` return `Set<string>`, so TypeScript can't distinguish them by default.

Library declaration from `lib.es2015.iterable.d.ts`:

```
interface SetConstructor {
new <T>(iterable?: Iterable<T> | null ): Set<T>;
}
```

Override to "knock out" the string constructor overload:

```
// declarations/ban-set-string-constructor.d.ts:
interface SetConstructor {
new (str: string ): void ;
}
```

Now constructing a `Set` with a string returns `void`, making downstream usage fail with a clear error:

```
const s = new Set('abc');
// ^? const s: void
console.log(s.has('abc'));
// ~~~ Property 'has' does not exist on type 'void'.
const otherSet: Set< string > = s;
// ~~~~~~~~ Type 'void' is not assignable to type 'Set<string>'.
```

Use an error string return and `@deprecated` for an even clearer signal:

```
interface SetConstructor {
/** @deprecated */
new (str: string ): 'Error! new Set(string) is banned.';
}

const s = new Set('abc');
// ^? const s: "Error! new Set(string) is banned."
```

This cannot produce a type error at the `new Set(...)` call site itself — that is a TypeScript limitation.

**Caveats:**

- Module augmentation only affects type checking. Runtime behavior of `JSON.parse` and `Set` is unchanged.
- Only use to make types stricter and more precise, or to disallow constructs. Adding declarations that don't reflect runtime reality creates confusion — incorrect types can be worse than no types (Item 40).
- "Knocking out" a method by making it return `void` won't work if the method already returns `void`.

This technique works for third-party `@types` and bundled declarations as well. See the `ts-reset` npm package for a collection of built-in type improvements.

**Things to Remember**

- Use declaration merging to improve existing APIs or disallow problematic constructs.
- Use void or error string returns to "knock out" methods and mark them @deprecated.
- Remember that overloads only apply at the type level. Don't make the types diverge from reality.
