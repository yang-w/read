**CHAPTER 10**

### Modernization and Migration

#### Item 79: Write Modern JavaScript

TypeScript compiles to any version of JavaScript, all the way back to ES5. This means you can use `tsc` as a transpiler: converting new JavaScript to older, more widely supported JavaScript. When converting an existing JavaScript codebase to TypeScript, there's no downside to adopting all the latest JavaScript features first.

**Use ECMAScript Modules**

Today there is one standard: ECMAScript modules, using `import` and `export`. If your JavaScript codebase still uses concatenation or another module system, switch to ES modules. TypeScript works best with ES modules, and adopting them allows you to migrate modules one at a time.

CommonJS to ES module conversion:

```
// CommonJS
// a.js
const b = require('./b');
console.log(b.name);
```
```
// b.js
const name = 'Module B';
module.exports = {name};
```

```
// ECMAScript module
// a.ts
import * as b from './b';
console.log(b.name);
```
```
// b.ts
export const name = 'Module B';
```

You can adopt ES modules in your TypeScript without adopting them in the generated JavaScript. Setting `module: "commonjs"` in `tsconfig.json` compiles the second code sample to the first.

**Use Classes Instead of Prototypes**

TypeScript struggles with prototype-based class patterns but understands the ES2015 class syntax with minimal annotations.

Instead of:

```
function Person(first, last) {
this .first = first;
this .last = last;
}
```
```
Person.prototype.getName = function () {
return this .first + ' ' + this .last;
}
```
```
const marie = new Person('Marie', 'Curie');
console.log(marie.getName());
```

Write:

```
class Person {
constructor(first, last) {
this .first = first;
this .last = last;
}

getName() {
return this .first + ' ' + this .last;
}
}
```
```
const marie = new Person('Marie', 'Curie');
console.log(marie.getName());
```

The TypeScript language service offers a "Convert function to an ES2015 class" quick fix for older-style classes.

**Other Features**

- Use `let` and `const` instead of `var`. `var` has quirky scoping rules.
- Use `for-of` or array methods like `map` instead of C-style `for(;;)` loops. The index variable is often unnecessary and C-style loops don't adapt as well to iterators.
- Use `async` and `await` for asynchronous functions instead of callbacks or raw Promises.
- Prefer arrow functions to function expressions — more concise and preserve the `this` value from surrounding context.
- Use default parameter values directly in the declaration (`function foo(param=123) {}`). TypeScript can infer the parameter's type from the default value.
- Use compact object literals and destructuring assignment. Write `{x}` instead of `{x: x}`. Write `[x, y] = pair` to unpack array values. Works particularly well with TypeScript tuple types.
- Use `Map` and `Set` instead of objects for associative arrays, to avoid problems from JavaScript's conflation of objects and associative arrays (e.g., reading the key `"constructor"` from a plain object).
- Use optional chaining (`x?.y`) instead of `x && x.y`. Use `fn?.()` to conditionally call a possibly-undefined function.
- Use nullish coalescing (`??`) instead of `||` for default values. If `x` is `0`, then `x || 10` evaluates to `10`, whereas `x ?? 10` evaluates to `0`. Use `??` when you want to check for null/undefined specifically, not general falsiness.
- Don't use `"use strict"`. TypeScript is stricter than strict mode, and it automatically includes `"use strict"` in its output when in module mode. Adding it to TypeScript source has no effect.

**Things to Remember**

- Adopt ES modules (`import`/`export`) and classes to facilitate your migration to TypeScript.
- Use TypeScript to learn about language features like classes, destructuring, and `async`/`await`.

#### Item 80: Use @ts-check and JSDoc to Experiment with TypeScript

`@ts-check` directs the type checker to analyze a single JavaScript file and report issues, without converting it to TypeScript. It is looser than TypeScript with `noImplicitAny` off.

```
// @ts-check
const person = {first: 'Grace', last: 'Hopper'};
2 * person.first
// ~~~~~~~~~~~~ The right-hand side of an arithmetic operation must be of type
// 'any', 'number', 'bigint' or an enum type
```

**Undeclared Globals**

```
// @ts-check
console.log(user.firstName);
// ~~~~ Cannot find name 'user'
```

Fix by creating a type declaration file (e.g., `types.d.ts`):

```
interface UserData {
firstName: string ;
lastName: string ;
}
declare let user: UserData;
```

Ensure `tsconfig.json` includes this file. This `types.d.ts` file models the environment where your code runs and becomes the basis for your project's type declarations.

**Unknown Libraries**

```
// @ts-check
$('#graph').style({'width': '100px', 'height': '100px'});
// Error: Cannot find name '$'
```

Install the type declarations for the library:

```
$ npm install --save-dev @types/jquery
```

Now the error is library-specific:

```
// @ts-check
$('#graph').style({'width': '100px', 'height': '100px'});
// ~~~~~ Property 'style' does not exist on type 'JQuery<HTMLElement>'
```

(The correct method is `.css`, not `.style`.)

Make sure to install types for the version of the library you're using.

**DOM Issues**

```
// @ts-check
const ageEl = document.getElementById('age');
ageEl.value = '12';
// ~~~~~ Property 'value' does not exist on type 'HTMLElement'
```

`document.getElementById` returns `HTMLElement`, but only `HTMLInputElement` has a `value` property. Since this is still a `.js` file, you can't write `as HTMLInputElement`. Use a JSDoc type assertion instead:

```
// @ts-check
const ageEl = /** @type {HTMLInputElement} */ (document.getElementById('age'));
ageEl.value = '12'; // OK
```

The parentheses after the comment are required.

**Inaccurate JSDoc**

When `@ts-check` is enabled, TypeScript checks your existing JSDoc comments:

```
// @ts-check
/**
* Gets the size (in pixels) of an element.
* @param {Node} el The element
* @return {{w: number, h: number}} The size
*/
function getSize(el) {
const bounds = el.getBoundingClientRect();
// ~~~~~~~~~~~~~~~~~~~~~
// Property 'getBoundingClientRect' does not exist on type 'Node'
return {width: bounds.width, height: bounds.height};
// ~~~~~ Type '{ width: any; height: any; }' is not
// assignable to type '{ w: number; h: number; }'
}
```

Two errors here:
- `getBoundingClientRect()` is defined on `Element`, not `Node`. The `@param` tag needs to be updated.
- Mismatch between `@return` tag (`w`, `h`) and the implementation (`width`, `height`).

The TypeScript language service can infer type annotations as a quick fix. For example:

```
function double (val) {
return 2 * val;
}
```

Applying the quick fix produces:

```
// @ts-check
/**
* @param {number} val
*/
function double (val) {
return 2 * val;
}
```

The inferred annotation is not always what you want. For complex parameters, the inferred type may be overly structural:

```
function loadData(data) {
data.files.forEach( async file => {
// ...
});
}
```

Quick fix result:

```
/**
* @param {{
* files: { forEach: (arg0: (file: any) => Promise<void>) => void; };
* }} data
*/
function loadData(data) {
// ...
}
```

This is structural typing gone awry. The intent was most likely `{files: string[]}`. Avoid over-typing with JSDoc — the goal is to convert to `.ts`, not to JavaScript with JSDoc annotations.

**Things to Remember**

- Add `"// @ts-check"` to the top of a JavaScript file to enable type checking without converting to TypeScript.
- Recognize common errors: undeclared globals (create a `.d.ts`), unknown libraries (install `@types/`), DOM type mismatches, and inaccurate JSDoc.
- Use JSDoc annotations for type assertions and better type inference.
- Don't spend too much time getting your code perfectly typed with JSDoc. The goal is to convert to `.ts`.

#### Item 81: Use allowJs to Mix TypeScript and JavaScript

The `allowJs` compiler option lets TypeScript files and JavaScript files import one another. For JavaScript files, `allowJs` is extremely permissive — unless you use `@ts-check`, the only errors reported are syntax errors.

`allowJs` lets you introduce TypeScript into your build chain before you start making code changes, so you can run your tests as you convert individual modules.

**Setting up with common tools:**

With webpack, install `ts-loader`:

```
$ npm install --save-dev ts-loader
```

Configure in `webpack.config.js`:

```
module.exports = {
module: {
rules: [
{
test: /\.tsx?$/,
use: 'ts-loader',
exclude: /node_modules/,
},
],
},
// ...
};
```

With Jest, install `ts-jest` and configure `jest.config.js`:

```
module.exports = {
transform: {
'^.+\\.tsx?$': 'ts-jest',
},
};
```

With Node.js, use `ts-node`:

```
$ node -r ts-node/register main.ts
```

If your build chain is custom, specify `outDir` in `tsconfig.json`. TypeScript will generate pure JavaScript sources in a parallel directory that your existing build chain can run over.

**Things to Remember**

- Use the `allowJs` compiler option to support mixed JavaScript and TypeScript as you transition your project.
- Get your tests and build chain working with TypeScript before beginning large-scale migration.

#### Item 82: Convert Module by Module Up Your Dependency Graph

Convert modules going up the dependency graph: start with the leaves (modules that import no others) and move up to the root.

**Step 1: Install @types for third-party dependencies**

Third-party libraries are always leaves by definition. Install `@types` for them first:

```
npm install --save-dev @types/lodash
```

Match `@types` package versions to the library versions you use.

**Step 2: Add types for external API calls**

Type the return values of API calls early, since many types flow from them and are difficult to infer from context:

```
async function fetchTable() {
const response = await fetch('/data');
if (!response.ok) throw new Error('Failed to fetch!');
return response.json();
}
```

```
interface TabularData {
columns: string [];
rows: number [][];
}
async function fetchTable(): Promise<TabularData> {
const response = await fetch('/data');
if (!response.ok) throw new Error('Failed to fetch!');
return response.json();
}
```

**Ordering your migration**

- Visualize the dependency graph (e.g., using `madge`).
- Run a topological sort for a precise conversion order.
- Focus on adding types, not refactoring. Note code smells, file bugs, and fix them later. Use `any` or `@ts-expect-error` temporarily if needed.

**Undeclared Class Members**

JavaScript classes don't require member declarations; TypeScript classes do. Renaming a `.js` file to `.ts` will produce errors for every property reference:

```
class Greeting {
constructor (name) {
this .greeting = 'Hello';
// ~~~~~~~~ Property 'greeting' does not exist on type 'Greeting'
this .name = name;
// ~~~~ Property 'name' does not exist on type 'Greeting'
}
greet() {
return `${ this .greeting} ${ this .name}`;
// ~~~~~~~~ ~~~~ Property ... does not exist
}
}
```

Use the "Add all missing members" quick fix. It adds declarations based on usage:

```
class Greeting {
greeting: string ;
name: any ;
constructor (name) {
this .greeting = 'Hello';
this .name = name;
}
greet() {
return `${ this .greeting} ${ this .name}`;
}
}
```

TypeScript inferred `greeting: string` correctly, but `name: any` needs to be fixed manually. After applying the quick fix, review and correct all `any` types.

**Values with Changing Types**

```
const state = {};
state.name = 'New York';
// ~~~~ Property 'name' does not exist on type '{}'
state.capital = 'Albany';
// ~~~~~~~ Property 'capital' does not exist on type '{}'
```

Fix by building the object all at once:

```
const state = {
name: 'New York',
capital: 'Albany',
}; // OK
```

If building at once is not feasible, use a type assertion temporarily:

```
interface State {
name: string ;
capital: string ;
}
const state = {} as State;
state.name = 'New York'; // OK
state.capital = 'Albany'; // OK
```

Leave a TODO comment or file a bug to refactor the assertion later.

**Losing type safety when converting from JSDoc + @ts-check**

With `@ts-check` enabled, JSDoc types are enforced:

```
// @ts-check
/**
* @param {number} num
*/
function double (num) {
return 2 * num;
}
```

```
double ('trouble');
// ~~~~~~~~~
// Argument of type 'string' is not assignable to parameter of type 'number'
```

When you convert to TypeScript and remove `@ts-check`, the JSDoc `@param` is no longer enforced. The parameter's type becomes implicitly `any`:

```
/**
* @param {number} num
*/
function double (num) {
return 2 * num;
}
```

```
double ('trouble'); // OK
```

Use the "Copy JSDoc annotations to TypeScript type annotations" quick fix to migrate types, then remove the JSDoc to avoid redundancy:

```
function double (num: number ) {
return 2 * num;
}
```

```
double ('trouble');
// ~~~~~~~~~
// Argument of type 'string' is not assignable to parameter of type 'number'
```

Migrate your tests last. They sit at the top of the dependency graph (production code doesn't import them), and keeping them in JavaScript during migration confirms that TypeScript conversion is a pure refactor with no runtime behavior changes.

**Things to Remember**

- Start migration by adding `@types` for third-party modules and external API calls.
- Migrate modules from the bottom of the dependency graph upward. Visualize the graph to track progress.
- Resist the urge to refactor code as you uncover odd designs. Stay focused on TypeScript conversion; file bugs for future refactors.
- Be aware that converting from JSDoc + `@ts-check` to TypeScript can silently drop type enforcement. Use the quick fix to move JSDoc types into TypeScript annotations.

#### Item 83: Don't Consider Migration Complete Until You Enable noImplicitAny

TypeScript code without `noImplicitAny` is best thought of as transitional — it can mask real errors in type declarations.

**Example: silent type error without noImplicitAny**

After using the "Add all missing members" quick fix:

```
class Chart {
indices: any ;

// ...
}
```

You change `any` to `number[]` and no new errors appear:

```
class Chart {
indices: number [];

// ...
}
```

But this type is wrong. Usage elsewhere in the class reveals the problem:

```
getRanges() {
for ( const r of this .indices) {
const low = r[0];
// ^? const low: any
const high = r[1];
// ^? const high: any
// ...
}
}
```

Indexing into a `number` is allowed without `noImplicitAny`, silently producing `any`. The correct type would be `number[][]` or `[number, number][]`.

With `noImplicitAny` enabled, this becomes an error:

```
getRanges() {
for ( const r of this .indices) {
const low = r[0];
// ~~~~ Element implicitly has an 'any' type because
// type 'Number' has no index signature
const high = r[1];
// ~~~~ Element implicitly has an 'any' type because
// type 'Number' has no index signature
// ...
}
}
```

**Strategy for enabling noImplicitAny**

- Set `noImplicitAny` locally and fix errors incrementally.
- Track type coverage to measure progress.
- Run tests with every change and commit frequently.
- Fix errors going up the dependency graph (as in Item 82).
- Commit type corrections before committing the `tsconfig.json` change, until the error count reaches zero.
- Optionally, prioritize production code over unit tests, or use project references with distinct `tsconfig.json` files at different strictness levels for different parts of the project.

`noImplicitAny` is the most important strictness option. Your project gets most of the benefits of TypeScript even without adopting other settings like `strictNullChecks`.

**Things to Remember**

- Don't consider your TypeScript migration done until you adopt `noImplicitAny`. Loose type checking can mask real mistakes in type declarations.
- Fix type errors gradually before enforcing `noImplicitAny`. Give your team a chance to get comfortable with TypeScript before adopting stricter checks.
